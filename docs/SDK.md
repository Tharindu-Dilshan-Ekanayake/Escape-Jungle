# Platform SDK

You are integrating the Boxity SDK (a cross-game identity platform — login, avatars, friends/presence, synced settings, and "Gems" in-game currency) into THIS HTML5/JavaScript web game. The SDK is branded "Boxity" but exposes itself as the global `window.Legion.SDK`. Do a complete, working integration following this spec exactly.

REFERENCE IMPLEMENTATION (use this): a complete, self-contained working example that exercises EVERY API below is hosted at https://bloxity.io/test-game.html (standalone) and https://bloxity.io/g/test-game (embedded). If you can fetch URLs, fetch https://bloxity.io/test-game.html and copy its exact patterns — it is the canonical source of truth and is simpler to adapt than writing from scratch. The spec below describes what that file does.

SETUP
1. Add this script tag before the game's own code (in index.html <head> or just before the game bundle):
   <script src="https://sdk.bloxity.io/legion-sdk.min.js"></script>
2. Initialize ONCE on startup, before using any namespace:
   Legion.SDK.init({ gameSlug: 'MY_GAME_SLUG' });
   Replace MY_GAME_SLUG with the slug this game is registered under on bloxity.io. (When the game is embedded in an iframe on bloxity.io the slug is auto-provided, but always pass it so standalone hosting and Gems purchases work.)
3. The SDK runs in two modes: "embedded" (iframe in a Boxity page, routes via postMessage) and "standalone" (its own page, calls the Boxity API directly). Write the SAME code for both.
4. Load the SDK from https://sdk.bloxity.io as above in every environment. The same script works on prod, stage and local because it reads the environment it is told (ENVIRONMENTS below).

ENVIRONMENTS - Boxity runs as three environments: prod (bloxity.io), stage (stage.bloxity.io) and local. ONE build of this game must run unchanged in all three. The PLATFORM tells the game which environment it is in. The game must NEVER work it out from its own hostname, the referrer, a build flag or any URL.
- Browser: Legion.SDK.environment() -> { env: 'prod'|'stage'|'local', apiUrl, playUrl, portalUrl, staticUrl }. The SDK fills it from window.BLOXITY_ENV (Boxity injects it into the pages it serves) or the portal handshake (embedded), and returns prod when nothing was told. Legion.SDK.onEnvironmentChanged(cb) fires if the handshake tells it after init. Code that runs before the SDK loads reads window.BLOXITY_ENV through one helper with the same prod fallback.
- Server: read process.env.BLOXITY_ENV, BLOXITY_API_URL, BLOXITY_MATCHMAKER_URL, BLOXITY_PORTAL_URL and BLOXITY_STATIC_URL (Boxity hosting injects them on every deploy). Fall back to 'prod', https://api.bloxity.io, https://play.bloxity.io, https://bloxity.io and https://static.bloxity.io only when a variable is missing.
- Build EVERY Boxity URL from these values. Below, {apiUrl}, {playUrl}, {portalUrl} and {staticUrl} mean the told values. Never write api.bloxity.io, play.bloxity.io or static.bloxity.io into code, build config or .env files. Host names written for prod (bloxity.io/g/<slug>, <id>.play.bloxity.io, <id>.host.bloxity.io) have the same shape under stage.bloxity.io on stage.
- Local: inside the local portal (localhost:3000) the environment arrives in the handshake. A standalone local page sets it itself before the game's code: <script>window.BLOXITY_ENV = { env: 'local', apiUrl: 'http://localhost:4000', playUrl: 'http://localhost:2567', portalUrl: 'http://localhost:3000', staticUrl: 'https://static.bloxity.io' };</script>, injected by the dev server only (Vite: a plugin with apply: 'serve' and transformIndexHtml), never in a production build.
- A page Boxity does not serve or embed (e.g. a separate CrazyGames build) is told nothing and runs against prod.

DEPLOYING (prod + stage) - Ship from GitHub Actions in .github/workflows/deploy.yml. If the repo already has a Boxity deploy workflow, change that one; never add a second.
- Branches keep their meaning: main deploys the production channel, dev the playtest (dev) channel. Every push goes to BOTH platforms: prod always, and stage as well once the repo has the secret LEGION_DEPLOY_TOKEN_STAGE (stage is opt-in). Add a workflow_dispatch input "target" (staging | prod, default staging) so any branch can be deployed to one platform by hand.
- Run the platforms as separate jobs of one matrix with strategy.fail-fast: false, so a stage failure never blocks or undoes the prod deploy. A first "targets" job outputs the list: ["prod","staging"] when secrets.LEGION_DEPLOY_TOKEN_STAGE is set, otherwise ["prod"]; a manual run uses only the chosen target.
- Per target: prod uses the secret LEGION_DEPLOY_TOKEN with https://api.bloxity.io and https://legion.bloxity.io; staging uses LEGION_DEPLOY_TOKEN_STAGE with https://api.stage.bloxity.io and https://legion.stage.bloxity.io. A staging job must never read or fall back to the prod token; fail with a clear error if its token is empty.
- One build for both platforms: never pass an environment, API URL or base domain into the client build. Tag server images per platform (e.g. stage-prod-SHA on staging) so a staging build never replaces a production image.
- With the Boxity deploy action (.github/actions/bloxity-deploy) pass deploy-token, api-url and legion-url per target. With your own steps, POST {legion-url}/v1/apps/GAME_ID/deploy and {api-url}/v1/hosting/games/GAME_ID/frontend with that target's token.
- The full workflow template is on docs.bloxity.io under Environments > Release flow.

AUTH (Legion.SDK.auth)
- getUser() -> LegionUser | null. LegionUser = { _id, username, displayName?, email?, pfp?, avatar? }.
- getToken() -> JWT string | null (for your backend). isLoggedIn() -> boolean.
- showAuthPopup() -> Promise<user|null>. Auto-picks an in-game modal (embedded) or a popup window (standalone). Inside Boxity never call it: the Boxity toolbar handles signing in. Only a game that also runs outside Boxity calls it, from its own "Log in" button shown only there.
- logout(). Same rule: never call it inside Boxity.
- onUserChanged(cb) -> unsubscribe. cb(user|null). FIRES IMMEDIATELY with current state, then on every login/logout. Use this as the single source of truth for auth UI and to (re)load friends/avatar/balance.
- authenticateWithServer(url) -> Promise<json|null>. POSTs { token, user } to your backend so you can verify the identity server-side. Required if this game has its own server: the server trusts only the verified user, never an id the client sends.
Implementation: subscribe with onUserChanged; when a user logs in, show their displayName||username (and pfp) if the game shows the player, and load friends + avatar + gems balance. Inside Boxity, never draw Log in / Log out / Sign in / Sign out buttons: Boxity handles accounts (see Platform UI rules).

AVATAR / COSMETICS (Legion.SDK.avatar)
- getEquipped() -> { hatId, backId, skinId, headId, armLId, armRId, legLId, legRId, torsoId, hairId, maskId, neckId, chestId, waistId, handId, shoesId, faceId, pantsId, shirtId }. IDs are strings; '-1' / null / '' / 'undefined' mean NOT equipped (use default mesh).
- Individual getters: getHatId(), getBackId(), getSkinId() (default '-1'), getHeadId(), getArmLId(), getArmRId(), getLegLId(), getLegRId(), getTorsoId(), getHairId().
- getSkinTextureUrl() -> URL of the skin texture with the worn face, shirt and pants already drawn on. For other players build it yourself: {apiUrl}/v1/avatar/skin-texture/s{skinId or 0}[_pn{pantsId}][_sh{shirtId}][_fc{faceId}].png (segments in that order, omit empty ones; no face/shirt/pants -> /skins/{skinId}.png). Always load the body texture from this instead of /skins/{skinId}.png.
- Hair is its own slot (hairId), worn together with a hat. Load it exactly like a hat: /items/hats/{hairId}.obj + /textures/hats/{hairId}.png on bone Neck1 at local (0, 0.8, 0).
- Masks (masks, glasses, goggles, small face props) are their own slot (maskId), worn together with a hat and hair. Load exactly like a hat: /items/hats/{maskId}.obj + /textures/hats/{maskId}.png on bone Neck1 at local (0, 0.8, 0).
- Accessories: neck, chest, waist, hand, shoes. Mesh /items/{slot}/{id}.obj + texture /textures/{slot}/{id}.png. Right after player.glb loads (before any animation or proportions), capture each bone's rest transform in model space: restInverse = inverse(inverse(model.matrixWorld) * bone.matrixWorld). Attach each accessory under its bone with local matrix = restInverse(bone) * translate(origin): neck -> Spine2, origin (0, 4.8, 0); chest -> Spine2, (0, 3.6, 0); waist -> Spine1, (0, 2.4, 0); hand -> worn as a pair: the mesh on ArmL2_leaf plus a copy mirrored across x (restInverse(ArmR2_leaf) * scale(-1,1,1) * translate(origin)) on ArmR2_leaf, origin (0, 0, 0), following position and rotation only (not scale) - add it to the scene and every frame set its transform to compose(bone world position, bone world rotation, scale 1) * local; shoes -> worn as a pair exactly like hands, on LegL2_leaf plus a mirrored copy on LegR2_leaf, origin (0, 0, 0), position and rotation only.
- Do NOT use skeleton.boneInverses for accessory placement: the leaf bones' inverse binds in player.glb are 90 degrees off their rest pose, which puts hand items sideways.
- If you apply shoulderWidth / torsoScaleX / legOffsetX by editing skeleton.boneMatrices, those move vertices but not bones: move each hand copy sideways in character-local X by side * 0.8 * (2 * (shoulderWidth - 1) + 2 * (torsoScaleX - 1)) and each shoe copy by side * 0.8 * 0.6 * (legOffsetX - 1) (side = +1 left, -1 right), and scale neck/chest/waist items by torsoScaleX on X (restInverse * scale(tsx,1,1) * translate(origin)). If you apply them by moving bones, accessories follow automatically.
- getProportions() -> { height, shoulderWidth, armLength, legOffsetX, torsoScaleX, neckHeight, headScale } — all numbers defaulting to 1.0.
- setProportions(partial) -> Promise. Partial merge, clamped + persisted to the avatar (API when standalone, portal when embedded, localStorage for guests); onProportionsChanged fires. Ranges: height 0.5-1.6, shoulderWidth 0.5-1.5, armLength 0.05-3, legOffsetX -0.7-5, torsoScaleX 0.3-2, neckHeight 0.94-1.2, headScale 0.3-2.6.
- resetProportions() -> Promise. Sets every proportion back to 1.0.
- onAvatarChanged(cb) and onProportionsChanged(cb) -> unsubscribe. Re-skin/rescale the player model when these fire.
- showCustomizer() / hideCustomizer() / toggleCustomizer() / isCustomizerOpen().
- Own settings screen: Legion.SDK.settings.set({ master_volume 0-100, music_volume 0-100, graphics_quality 'Low'|'Medium'|'High'|'Ultra', show_fps, camera_sensitivity 0.1-5 }). Boxity saves them for every game; listeners fire as usual.
- Own skins screen (hub games): getInventory() -> Promise<{ signedIn, gems, items }> (everything the player owns; embedded, the portal answers). getShopItems({ type?, partSlot?, search?, offset?, limit? }) -> Promise<{ items, total, hasMore }> (the whole catalogue a page at a time, most popular first). Items are { id, name, type, partSlot?, iconUrl?, price, owned, equipped }. getShop() = inventory + first catalogue page. toggleItem(itemId) -> Promise<boolean> wears an owned item or takes it off (false if not owned). buyItem(itemId) -> Promise<boolean> buys an avatar item or emote through Boxity's purchase confirmation (false for guests or when the player backs out). Never charge players any other way.
- Custom characters: getEquipped().characterId (or getCharacterId()). A real id means the player wears their own uploaded character. getCharacter() (local player) / getCharacterFor(equipped) (other players) -> Promise<{ id, name, glbUrl, textureUrl, rig: { joints, anchors, height, fit?: { head, torso } } } | null>. Load glbUrl INSTEAD of player.glb: it has the same 22 bones, names and rest rotations, so every animation plays on it. Do not apply the skin texture, face/shirt/pants, body parts or proportions to it. Accessories keep their player.glb placement, fitted to the character. Head and torso items (bones Neck1, Spine1, Spine2): M = characterAccessoryMatrix(character, bone) (16 numbers, column-major); attach under the character's bone with local = M * modelPlacement, where modelPlacement is the item's placement in player.glb model space (hat/hair/mask: translate(0, 5.6, 0); back: translate(0, 4.2, 0); neck/chest/waist: translate(origin)). If M is null (older character), use scale(rig.anchors[bone]) * the standard local. Hands and shoes: local = scale(rig.anchors[bone]) * restInverseFromPlayerGlb(bone) * translate(origin) (capture restInverse from player.glb, not from the character). null -> draw the regular avatar. Replicate ids only, never URLs: if the game server filters equipped ids, add characterId to its list. Rebuild the rig (load the GLB once, SkeletonUtils.clone per player) when onAvatarChanged gives a new characterId. Use player.glb's scale (both are 6.4-unit rigs, feet at y 0) and no proportions. Wrist: rig.joints.ArmR2_leaf; head top: rig.fit.head.max[1]. On null or a failed GLB, draw the regular avatar.
Asset CDN (base {staticUrl}/avatars): hats, hair and masks mesh /items/hats/{id}.obj + texture /textures/hats/{id}.png; back /items/back/{id}.obj + /textures/back/{id}.png; accessories /items/{neck|chest|waist|hand|shoes}/{id}.obj + /textures/{neck|chest|waist|hand|shoes}/{id}.png; skin texture /skins/{id}.png (or getSkinTextureUrl() when a face, shirt or pants is worn); body parts head/torso /parts/{type}/{id}.glb; arms/legs /parts/{type}/{id}_L.glb and _R.glb; icons /icons/{id}.png; base body model /player.glb. Only load a slot if its id is a real equipped id (not '-1'/''/'undefined'/null).

GAME LIFECYCLE & ROOMS (Legion.SDK.game)
- loadingStep('text') while loading; loadingEnd() to dismiss the loading screen.
- gameplayStart() / gameplayEnd().
- updateRoom(roomId, partyId?) when joinable; updateRoom('') in menus. partyId is the GAME's own squad/team id, if it has one; it is NOT a Boxity party (never pass a Boxity launchId or roomKey here).
- playerJoined(username) / playerInRoom(username) from your netcode join handlers (shows friend-join toasts).

MULTIPLAYER CONNECTION (Legion.SDK.net) - REQUIRED if this game's server is hosted on Boxity (its backend is <id>.host.bloxity.io). Skip only for single-player games or servers hosted elsewhere.
- NEVER connect the game socket to <id>.host.bloxity.io (no new Client('wss://<id>.host.bloxity.io'), no joinOrCreate there, no VITE_SERVER_URL or similar pointing there). That is one fixed route to ONE pod: Boxity never sees the players and never starts a second pod, so once the game grows, joins get slow, then fail, and the pod restarts and disconnects everyone. Keep <id>.host.bloxity.io for HTTP only (auth, API calls, Boxity's webhooks).
- On EVERY connect: const { endpoint } = await Legion.SDK.net.resolveEndpoint('<id>'); const client = new Client(endpoint); const room = await client.joinOrCreate(ROOM_NAME, options); where <id> is the hosting id. Build a NEW Client from each resolve; each endpoint is pinned to one pod, so never reuse a Client from an earlier endpoint.
- If the resolve or the join fails, resolve again with a backoff (a cold start can take up to ~45 s; give up after ~60 s). If the room closes unexpectedly (not a normal leave), resolve again and rejoin.
- Use only the SDK to reach the matchmaker (no hand-written POST to /v1/play): it reuses the player's seat on retries and carries the party ticket.
- A page on <id>.dev.play.bloxity.io reaches the dev backend automatically. A frontend on its own domain reaches prod unless it passes { version: 'preview' }.
- SERVER IDENTITY - REQUIRED for every game server (hosted on Boxity or anywhere else): send Legion.SDK.auth.getToken() in the join options; in onAuth/onJoin the server calls POST {BLOXITY_API_URL}/v1/auth/game-token/verify (header Authorization: Bearer <token>, JSON body { gameSlug }) and uses ONLY the returned user._id as the player's account id for saves, stats, rewards and Gems. No token, or a refused one (401): the player is a guest with an id the SERVER makes (e.g. 'guest_' + sessionId) or a guest-only key, never an account. Never take userId/profileId/accountId from the join options as an account id, never jwt.decode() a token without checking its signature, and never fall back to a client-sent id when verify fails.
- The server keeps answering GET /health fast. Its room's maxClients is the game's ROOM SIZE (players per match, 2-100), chosen for the gameplay. Never set seatCap in the deploy: Boxity measures CPU per player and decides how many players (and how much CPU) each pod gets. Send the room size as roomSize in the deploy instead.

OPEN ROOMS ON THE GAME PAGE - Boxity lists a multiplayer game's live rooms under "Open Rooms" on its game page, each with a Join button.
- At launch, read ?roomId= from the page URL (new URLSearchParams(location.search).get('roomId')) and join that room directly. Boxity's Join button and friend invites both open the game with it. If the room is gone or full, fall back to normal matchmaking.
- Hosted on Boxity (Colyseus on Legion): the list fills itself from the room reporter (Server/src/legion-room-reporter.ts, installRoomReporter() after listen). If one backend serves several catalogue rows by ?mode=, set { mode: <int>, modeName } in each room's metadata. To join a hosted room by id, resolve its pod first (GET {playUrl}/v1/dir/<hostingId>/list returns each room's joinUrl), because a bare joinById can land on another pod.
- Hosted elsewhere: serve a public GET returning { rooms: [{ id, region, type: 'public'|'private', players, maxPlayers, locked }], onlineServers: [...] } across ALL your servers, honour ?mode=<n> if several catalogue rows share the backend, and ask Boxity to set it as the game's allRoomsUrl.

EMOTES - Boxity draws the emote picker itself; never build emote UI (no button, menu or wheel).
- On boot (not after assets load), call Legion.SDK.game.registerFeature('emotes'). The emote button only appears for games that registered.
- Legion.SDK.player.onEvent((event, data) => ...): when event === 'play_emote', data is the emote's catalogue id (24-char string). Play it on the local character and replicate it to other players with the game's existing player-state networking. Unsubscribe on teardown.
- Fetch {apiUrl}/v1/avatar/emotes once at startup: { id, name, price, free, icon, clip }, clip = { len, loop, tracks }, tracks maps bone name -> [[timeSeconds, xDeg, yDeg, zDeg], ...].
- Standard Bloxity rig (player.glb: ArmR_Offset, ArmR1, ArmR2, Spine1, Neck1, LegR1, LegR2 and L equivalents): values are DEGREE DELTAS over the bind pose, euler XYZ right-multiplied onto each bone's bind quaternion, smoothstep between keys (s*s*(3-2*s)), clamp outside the key range, loop wraps on time % len, ignore unknown bones. Own rig: map each emote to an existing animation by its name.
- Blend in over ~0.1s; stop when the player moves; ignore unknown ids silently and never throw; do not check ownership (Boxity only sends entitled ids); never hardcode emote ids.

PARTY PLAY (Legion.SDK.party) — Boxity parties (up to 6 friends) must land in ONE room, or Boxity refuses to launch them with "This game doesn't support party play yet".
- If this game is hosted on Boxity (Boxity serves its pages) and connects through the Boxity matchmaker (MULTIPLAYER CONNECTION above), party play is automatic once BOTH of these hold: (1) the SDK is loaded from https://sdk.bloxity.io/v1/legion-sdk.min.js (never a bundled copy) BEFORE the first matchmaker request; (2) the game room sets maxClients (2-100; not unlimited). Boxity learns the room size from players joining through the matchmaker, so a game that connects anywhere else is treated as not supporting party play. Skip the rest of this block.
- Otherwise (own servers): on boot call Legion.SDK.party.enable({ maxPartySize: <most players one room holds> }). Before joining a room: const party = await Legion.SDK.party.getLaunch() -> null (solo) or { launchId, roomKey, size, members[{userId, username, displayName?}], starterId, isStarter, managed }. If party && !party.managed, put every player sharing party.roomKey into ONE room that fits party.size and that strangers cannot join (members arrive in any order, over up to a minute). Then call Legion.SDK.party.joined(room.id) with the same id for every member. If you cannot seat them together, call Legion.SDK.party.failed('room-full') instead of splitting them. Boxity verifies every launch and switches party play off for 7 days after 2 failures in a row.

CRAZYGAMES & PLAY WITH FRIENDS — Boxity also runs on CrazyGames (bloxity.io/?cg=true and the /mini site). Build for it by default.
- Play with friends (CrazyGames "instant join"): the first player expects a NEW private room their friends can join at once. A hosted game that follows MULTIPLAYER CONNECTION above (SDK loaded by script tag before the game's code, Legion.SDK.net.resolveEndpoint, then joinOrCreate) gets this from Boxity with NO extra code: Boxity's matchmaker opens a fresh private room and seats every invited friend in it. Keep it working: never pick a room by id yourself except for ?roomId= (OPEN ROOMS above); never move players to another room on your own (start the next round in the SAME room); give the room a maxClients of 2-100; never connect to <id>.host.bloxity.io. A game that breaks these is detected after two launches and stops being offered.
- Only if this game makes its OWN private rooms instead: when the page URL has ?instantMultiplayer=true, create a NEW private room at once (client: client.create(ROOM_NAME, { ...options, private: true }); server: this.setPrivate(true) in onCreate when options.private, and keep an EMPTY private room alive ~30 s so a reconnect can return to it). As soon as the player is in it, call Legion.SDK.game.updateRoom(relayRoomId + '~' + colyseusRoomId). Then, on boot, call Legion.SDK.game.registerFeature('play_with_friends') - only once all of this works.
- Invites: a friend who accepts a CrazyGames invite opens the game with ?roomId= exactly like Boxity's Join button. Nothing extra to build.
- Signing in mid-game: CrazyGames players often sign in after they start playing. If the game reconnects to apply the new identity (onUserChanged), rejoin the SAME room by id: new Client(Legion.SDK.environment().playUrl.replace(/^http/, 'ws') + '/v1/ws/' + relayRoomId).joinById(colyseusRoomId, options). Fall back to normal matchmaking only if that room is gone. Re-matchmaking would pull the player out of their friends' room.
- Guest progress: CrazyGames players start as Boxity guests. When that browser signs in to an account that already existed, the guest's progress should follow. On your server, verify the player with POST {BLOXITY_API_URL}/v1/auth/game-token/verify (header Authorization: Bearer <Legion.SDK.auth.getToken()>, JSON body { gameSlug }) -> { valid, user, carriedFrom? }. carriedFrom lists up to 5 Boxity guest user ids this browser played as before signing in (last 30 days). If the account has NO progress in this game yet, copy the first guest's progress into it, then mark that guest save as used so it can never be copied into a second account. If the account already has progress, leave it untouched.
- Controls on CrazyGames: ESC exits fullscreen and P opens Boxity's pause menu. Never bind P, and do not show your own fullscreen button there.
- Optional CrazyGames build: Boxity loads the game's CrazyGames URL (set in the game's dashboard entry, e.g. this game's URL + ?cg=true) on CrazyGames. Read ?cg=true from the game's OWN location to leave out anything you do not want on CrazyGames. Keep one bundle for both.

DEATH SCREEN (Legion.SDK.deathScreen) - REQUIRED in every game where the player can die. Boxity shows ads around the game while the player is dead, and the game's own Respawn button waits for Boxity's countdown (at least 4 s) so the ads are seen.
- When the local player dies: const death = Legion.SDK.deathScreen.show(). Keep the game's own death UI (kill cam, killer card, extra buttons) and its own Respawn button, in the game's own style. Never respawn the player automatically on a timer.
- death.onCountdown(n => ...) -> unsubscribe: n is the seconds left (4, 3, 2, 1) and 0 when the player may respawn. Show n on the Respawn button (e.g. a number or ring) and keep the button inactive until n === 0 (or await death.ready).
- When the button is pressed: if (death.respawn()) respawnPlayer(). respawn() returns false (and does nothing) while the countdown is running; respawn ONLY on true. Never respawn the player any other way while a death screen is open.
- If the round ends or the player leaves to a menu while dead, call Legion.SDK.deathScreen.hide() instead of respawning.
- Keep the death UI in the CENTRE of the screen: Boxity puts the banners along the edges (top, sides, corners), and an ad may cover anything there. Clicks outside the banners reach the game.
- Outside Boxity, or when Boxity runs no death screen ads, the countdown is 0 at once and respawn() returns true, so this one code path works everywhere. Boxity's menu "Reset Character" (respawn_request below) is separate and stays instant.
- Optional: Legion.SDK.deathScreen.show({ sizes: { 'middle-left': '160x600' } }) prefers a banner size at a position; Boxity uses it only where its admins allow that size.

AD BREAKS (Legion.SDK.ads) - REQUIRED in every game. Boxity runs every ad itself, over the game; never load an ad script or draw your own ads.
- Once, right after init: Legion.SDK.ads.onBreakStart(() => { pause the simulation; mute all audio }) and Legion.SDK.ads.onBreakEnd(() => { resume; restore audio }). Boxity may start a break at any time, whether or not the game asked.

REWARDED ADS (Legion.SDK.ads.showRewarded) - REQUIRED when the game has rewards a player could earn by watching an ad (revive, extra life, boost, coins, a free spin).
- Show the "Watch ad" button only while Legion.SDK.ads.isAvailable() is true.
- const r = await Legion.SDK.ads.showRewarded('revive'); the placement name is lowercase letters, digits and hyphens only (NO underscores). It never rejects. Grant ONLY when r.status === 'completed'; anything else ('skipped', 'no-fill', 'blocked', 'error', 'denied' with r.reason, 'disabled') means no ad was watched, so keep the button and say "try again later".
- A game with its own server grants the reward on the server: send r.rewardToken with the request, and the server calls POST {BLOXITY_API_URL}/v1/ads/reward/verify with JSON { gameSlug, rewardToken } and grants only when the answer has valid: true. A token verifies once, for this game only, within 5 minutes; userId in the answer is the Boxity account id or null for a guest. No token = Boxity could not issue one: do not grant a server-side reward without it. In a Create preview r.test is true and the token verifies only while the game is unpublished.

SCREEN ADS (Legion.SDK.ads.declareScreens + Legion.SDK.ads.screen) - REQUIRED in every game. The game lists its screens once and reports each one as it opens; Boxity shows banners around it. The game sets where banners start; Boxity's admins can change anything (positions, sizes, on/off, per platform and per game) without a new build.
- Once, right after init, list EVERY screen the game has: Legion.SDK.ads.declareScreens({ menu: { slots: [{ position: 'middle-left', sizes: ['300x600', '160x600'] }, { position: 'bottom-center', sizes: ['728x90', '320x50'] }] }, results: {}, gameplay: {} }). A screen left out means the game does not have it, and admins cannot manage it, so list them all. Always list gameplay. Ask the developer which screens the game has if it is not clear from the code.
- slots is optional for each screen: an empty {} uses Boxity's layout. Each slot is a position plus the sizes to try in order. Use any position (top-left, top-center, top-right, middle-left, middle-right, bottom-left, bottom-center, bottom-right) and any size (300x250, 728x90, 300x600, 320x50, 320x100, 160x600). The centre stays free for the game, and Boxity's toolbar sits at the top-left.
- GAMEPLAY ADS ARE OFF BY DEFAULT. Report the gameplay screen anyway, so Boxity can manage it. Ask the developer whether they want banners while playing; only if they do, declare gameplay: { show: true }. Never turn it on unasked.
- Every time a declared screen opens, gameplay included: Legion.SDK.ads.screen(type) with type 'menu' (title/start menu with Play), 'lobby' (waiting for players, matchmaking, pre-round countdown), 'results' (round over, level complete, game over, scoreboard), 'panel' (a full-screen in-game panel: leaderboard, shop, inventory, upgrades, quests) or 'gameplay' (actively playing). It returns a screen with .state ('pending', 'showing', 'closed'), .onStateChange(cb) and .hide().
- One screen shows at a time: calling screen() again replaces the previous screen's banners. When a screen closes and nothing replaces it, call .hide() on it or Legion.SDK.ads.hideScreen().
- Keep every screen's own UI in the CENTRE: banners sit along the edges (top, sides, corners) and may cover anything there. Pass { skip: ['top-right'] } to keep a position free for the game's own UI, and { sizes: { 'middle-left': '160x600' } } to prefer a size at a position (used only when that size is on the position's list; admins' own layouts ignore both options). Positions: top-left, top-center, top-right, middle-left, middle-right, bottom-left, bottom-center, bottom-right.
- While the player is dead the death screen draws over these banners. Outside Boxity screen() does nothing (state 'closed'), so one code path works everywhere.

LEADERBOARDS (Legion.SDK.leaderboard) - REQUIRED in every game with a score players compete on (points, coins, kills, best time, level reached, items collected...). Ask the developer whether the game has such a score and which boards it should have; do not guess. Record the answer as hasScore: true or false in BLOXITY_CODE_METADATA.md (frontmatter). Boxity shows the boards on the game page and behind a trophy button in the in-game toolbar.
- Right after Legion.SDK.init(), declare every board once: Legion.SDK.leaderboard.define([{ id, label, order, mode, format, reset }]). id: lowercase a-z, 0-9, _ or - (max 32), permanent. label: what players see ("Coins", "Best time"). order: 'desc' (higher wins, default) or 'asc' (lower wins, e.g. times). mode: 'best' (default, keeps each player's best), 'sum' (adds up every submitted amount, e.g. kills this week) or 'latest'. format: 'number' (1,234, default), 'compact' (1.2M, for big currencies) or 'time' (milliseconds shown as 1:23.45). reset: 'none' (All Time only, default), 'daily', 'weekly' (Monday 00:00 UTC) or 'monthly'; a resetting board also keeps All Time. At most 10 boards. Call define() even when the server submits the scores: it is what shows the trophy button.
- The FIRST declaration creates a board. Later changes to an existing board's settings in code are ignored (the developer edits boards in the Boxity dashboard), so choose ids and settings carefully.
- Submitting: when the game has its own server on Boxity hosting, submit from the SERVER (below), from state the server owns, never from a client packet. Otherwise submit from the browser: await Legion.SDK.leaderboard.submit(id, score) when a score is final (end of a run, round or level, an item banked) - not every frame. For mode 'sum' send the amount just gained (e.g. 1); for 'best' and 'latest' send the score itself. It resolves to { board, results: [{ period: 'current'|'all', rank, score, improved }] }, or null when there is no Boxity player. Optionally celebrate improved results ("New best! #12").
- Server: POST {BLOXITY_API_URL}/v1/leaderboards/hosted/{BLOXITY_GAME_ID}/report with Authorization: Bearer {BLOXITY_REPORT_TOKEN} and JSON { "boards": [same declarations, optional], "scores": [{ "board", "userId": "legion_<id>", "score" }] } (max 200 scores per call). Batch (e.g. every 10-30 s and at round end). Only report "legion_" identities and strip any "#m..." mode suffix. Read BLOXITY_API_URL as process.env.BLOXITY_API_URL || 'https://api.bloxity.io'. Log the response's "dropped" counts. Without BLOXITY_REPORT_TOKEN (local dev) do nothing.
- Reading: Legion.SDK.leaderboard.getTop(id, { period: 'current'|'all', limit }) -> { rows: [{ rank, username, displayName, pfp, score }], me, resetsAt, total }; getMine(id) -> the player's own row or null. A game button can open Boxity's full leaderboard panel: Legion.SDK.leaderboard.open(id) (false outside Boxity; then hide the button or draw a list with getTop).
- Boxity sets no score limits and does not police scores: fairness is the game's job. Guests rank too, and their scores follow them when they sign in.

CHAT (Legion.SDK.chat) — Boxity draws the chat UI over the game; never build your own chat box while embedded. Show each player's latest message above their character instead.
- onMessage((m) => {...}) -> unsubscribe. m = { userId, username, text, isGif, at, isLocalPlayer }. Every message in the player's current room, the sender's own included. The sender is verified by Boxity and the text is already filtered. Subscribing is the opt-in.
- userId is the sender's Boxity account id, the same id (token sub) your server verifies. Key your players by it; strip any prefix you add (e.g. 'legion_').
- Show Legion.SDK.chat.bubbleText(m) (two short lines, or 'sent a GIF') above that player's head for Legion.SDK.chat.bubbleSeconds (4) seconds; a newer message from the same player replaces it. three.js: Legion.SDK.chat.attachBubble(THREE, player.root, Legion.SDK.chat.bubbleText(m)) does all of this. If the game draws name tags, put the bubble just above the tag instead.

GEMS PURCHASES (Legion.SDK.gems; Legion.SDK.bux is a deprecated alias) — server-authoritative.
- requestPurchase(sku, metadata?) -> Promise<{ success, transactionId?, error? }>. Pass ONLY the sku (e.g. 'coins_500'); the price comes from the server catalog selected by gameSlug. On success, grant the item locally and record transactionId.
- getBalance() -> Promise<number>.
- Fulfillment is delivered by a server-to-server webhook to your game server (POST JSON: transactionId, userId, username, gameSlug, sku, productName, productPrice, metadata, timestamp; header x-legion-webhook-secret when configured). Your server MUST return 2xx or the Gems are auto-refunded. If this game has a backend, also add/verify that webhook endpoint. On Boxity hosting the webhook can land on ANY of the game's pods, not the buyer's: record the grant in the database (MONGODB_URI) keyed by transactionId, answer 2xx, and have each pod apply unapplied grants for the players it holds. Never look the buyer up in one pod's memory.
